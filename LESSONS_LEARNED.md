# LESSONS_LEARNED — meeting-scribe

Bug journal + key decisions. Read before debugging. Format: what broke / root cause / fix / where.

## Architecture decisions (why the stack is what it is)

- **Fork ownscribe, don't greenfield.** It already ships the hardest part — macOS audio capture with separate mic+system taps, whisperx+pyannote pipeline, per-speaker Markdown/JSON output. Building from scratch was over-engineering.
- **Whisper large-v3, NOT turbo, NOT Parakeet, NOT Canary.** large-v3 wins on FR/EN. Turbo's pruned decoder is weaker on French. Parakeet has NO language conditioning → involuntarily TRANSLATES spontaneous French to English (silent falsification — disqualifying). Canary was a real A/B candidate (has source_lang) but the pilot on real code-switched audio showed it LOSES by 66pts on switch spans → whisperx stays default.
- **Capture = CoreAudio process tap (macOS 14.2+), NOT ScreenCaptureKit.** SCK requires Screen Recording permission even for audio-only. The CoreAudio tap uses the audio-only permission (assures the user the app can't see the screen) AND is testable headless. SCK kept as a <14.2 fallback.
- **Your voice vs the call = TWO PHYSICAL SOURCES**, not diarization: your mic (what you send) = mic.wav = "Owner", the system tap (what you receive) = system.wav = diarized. Perfect separation by construction — but only on HEADPHONES (see echo below).
- **Diarization: pyannote community-1 on CPU, never MPS.** The whole ASR path is CPU-bound anyway (CTranslate2 has no Metal backend), so forcing CPU costs nothing extra. MPS re-test deferred to the token pass.
- **Naming reuses pyannote's own per-cluster embeddings** (DiarizationPipeline return_embeddings=True) — no separate ECAPA/SpeechBrain dependency.

## Verification lessons (2026-07-28, the Glass batch — 5 builders, 4 reopened tasks)

- **A claim about APPEARANCE requires LOOKING. This was violated TWICE in one day, the second time
  immediately after documenting the first.** Round one: `TODO.md` said the Glass design was
  delivered, on the strength of *"standard components carry Liquid Glass automatically"*. The
  deployment target had indeed been raised; the reasoning was that Glass therefore arrived free. It
  did not — Glass is a LAYOUT (avatars, envelope strip, type scale, glass on rails). The user opened
  the app and saw stock SwiftUI in seconds. Round two, hours later: the appearance work was done,
  the suite was green at 262, and the status line was rewritten to *"the window now looks like the
  design you validated"* — again with **nobody having looked**. The user rejected it on sight: "le
  design est pas bon du tout, tu n'as pas fait de vérif de design réel."
  The failure is not carelessness about a fact, it is **substituting an available proof for the
  required one**. A green suite, 3 `glassEffect` call sites and a symbol present in the binary all
  prove the code RUNS. None of them is evidence about how it READS. When the only honest answer is
  "nobody has looked", write that — "unverified" costs one line; a false claim costs the user's
  trust in every other line. Corollary: correcting a claim-without-evidence by writing a *different*
  claim-without-evidence is not a correction, it is the same error with new wording.
- **A test surviving a mutation only means something if it COULD have failed it.** A reviewer
  reported 5 `MeetingInspectorConfigFormatTests` as false greens because breaking *single*-quote
  TOML stripping left them all green. But those tests write `format = "markdown"` / `"json"` with
  **double** quotes — `grep -c "'"` on the file returns **0** — so the mutation changed a branch none
  of them reach. That is an **irrelevant mutation**, the opposite of a false green: a false green is
  "I broke what it guards and it did not notice", this was "I broke something else and the tests
  correctly did not care". The mutation that actually targeted their claim — `let filename =
  "summary.md"`, ignoring the parsed format — turned the suite **red with 7 failures**, with the
  two JSON tests firing and the three markdown ones correctly still green because they *assert*
  markdown. So the suite genuinely guards format resolution. One grep for the input that reaches
  the mutated line settles this in seconds, and the trap is strongest **immediately after a true
  finding**: the same reviewer's previous finding was real, and pattern-matching it onto a file with
  different inputs is how a good finding manufactures a false one.
- **"Another suite already covers it" is only true if that suite RUNS.** I waived 6
  `TestComputeRMSEnvelope` tests as redundant-but-harmless, on the grounds that the real e2e suite
  covers the same function on real data. An independent reviewer refuted it: that suite is
  `@pytest.mark.hardware`, so `scripts/check.sh` **skips** it. On every normal run — which is every
  run that gates a commit — those 6 tests are the *only* coverage `compute_rms_envelope` has. The
  waiver was not merely wrong, it was inverted: I had classified the load-bearing tests as the
  redundant ones. Before calling coverage redundant, check the *marker* on the suite you are
  crediting and whether the gate you care about executes it.
- **`tail` on a test run destroys the number you are trying to read, and inside a redirect it
  destroys it permanently.** Reading the Swift total with `swift test | tail -8` shows only the
  swift-testing block — 19 tests — because the XCTest bundle total is followed by hundreds of
  per-test lines. Worse: `swift test > file 2>&1 | tail -8` writes the *truncated* text to disk, so
  the real count is gone and cannot be recovered without re-running. I did this twice in one session
  and briefly believed a 291-test suite was 19 tests. **This package prints TWO independent totals**
  — an XCTest bundle line and a `Test run with N tests` line for swift-testing — so reading either
  alone understates the suite. Every "276 Swift" in this file's history was XCTest-only; the real
  figure is 291 passing + 4 skipped. Redirect the whole run to a file, then grep the file, and count
  test *cases* rather than summing `Executed N tests` lines (per-suite and per-bundle lines both
  match, so summing double-counts). Same family as the `timeout`-returns-127 trap: verify what the
  command actually DID before quoting what it said.
- **`pytest -k "Class::method"` silently selects NOTHING, and reports it as success.** `CLAUDE.md`
  documented `-k "TestRankMeetings::test_speaker_boost"` as the way to run a single test; measured, it
  gives `636 deselected in 0.23s` and **exit 0**. `-k` takes a boolean expression over names, so `::`
  matches no test — but a run that selected zero tests looks exactly like a run that passed, which is
  how it survived in the docs. The working forms are the path (`tests/test_search.py::TestRankMeetings::test_speaker_boost`)
  or `-k "TestRankMeetings and test_speaker_boost"`. Same family as the `timeout`-returns-127 trap:
  **check that the command DID the work before reading its exit code as a result** — for pytest, that
  means reading the selected/deselected counts, not just the green.
- **A stale number propagates through every reader, including auditors.** `TODO.md` and `HANDOFF.md`
  both carried "630 Python + 276 Swift" for long enough that a reviewer sent to audit the docs
  re-measured Python (catching 635) but *accepted* 276 from the document it was auditing — so the
  audit confirmed a wrong number as correct. An inherited figure is not evidence; re-derive each one
  in the turn you cite it.
- **Sabotage the production function, not the test.** Two builders reported COMPLETE on tests that
  guarded nothing. Replacing `loadEnvelope()` with `return nil` — W0-5 completely dead — left all
  SIX tests green, because they rebuilt `try? EnvelopeDocument(contentsOf:)` themselves and asserted
  on their own local variable. Reading the diff would never show this. The question is not "does the
  test pass" but "does the test fail when I break the thing it names".
- **A survived mutation, reported, is worth more than a passed one.** `builder-badge` predicted its
  call-site mutation would go red, ran it, got GREEN, and published that against its own prediction.
  That single honest report was more useful than the two "COMPLETE" claims I had to sabotage myself.
  The corollary: a builder that reports only green results has not run the mutation that would
  embarrass it.
- **A FALSE GREEN is as real as a false red, and rarer to suspect.** My first mutation of `BadgeText`
  came back green. Wrong conclusion available: "the test is dead". Truth: an agent had rewritten the
  file one second earlier, so the compiled binary held its restored code, not my mutation. Fix:
  `stat -f "%Sm %N" -t "%H:%M:%S" <file>; date +%H:%M:%S`, wait for ~40s of quiet, re-verify the
  mutation is ON DISK with `sed`, then measure. Without that I would have rejected a correct fix.
- **Sixth phantom red, same cause.** A builder declared itself blocked by a compile error in
  `SummaryDocument.swift`; `swift build` two minutes later: `Build complete! (0.16s)`. It had read a
  file another agent was mid-write. It then EDITED that file, which is how the next phantom gets
  manufactured. Sequencing rule that actually works: never let two agents own one file — block the
  task instead. Task #4 was held behind #2/#3 for exactly this and produced no phantom.
- **Also this batch:** a `Button` wired to an empty function body (fifth instance of "plumbed to a
  consumer never assigned"); the Python half of the same absent-vs-zero defect the UI had, sitting
  UPSTREAM where no reader could compensate; and `?? 0` at a render site silently defeating a
  deliberate `Int?` three commits after it was chosen. **When a type encodes "unknown", grep every
  render site for `??` before believing the guarantee holds.**

## Bugs caught by REAL runs (not synthetic tests) — the highest-value catches

- **BUG0 (CRITICAL): the CoreAudio tap FROZE Zoom + no permission prompt fired.** First live-call test: starting the tap froze Zoom so hard the user couldn't join; Ctrl+C released it instantly. Root cause: the CLI binary had NO embedded Info.plist → no NSAudioCaptureUsageDescription → macOS had nothing to prompt with → the unauthorized tap stalled CoreAudio (~60s, per Chromium's documented behavior on the same API) which froze every audio client. Fix: embed the Info.plist via `-sectcreate __TEXT __info_plist` (verified present in the shipped binary via otool + strings) + a CGPreflightScreenCaptureAccess fail-loud guard before tap creation. On macOS 26.1+/27 the tap rides the existing Screen Recording grant, so no prompt fires on an already-granted machine (expected, not a bug). A synthetic tone test could NEVER have caught this — needed a real call with a real competing audio client.
- **BUG1: no speaker labels on `resume`.** Was the COMMAND, not the pipeline — `resume`/`reprocess` had no `--diarize` flag so diarization stayed off by default. Fix: thread `--diarize` through both. Lesson: verify a "broken feature" is actually enabled before debugging the engine.
- **BUG2: summary hallucinated names/action-items.** phi-4-mini invented John/Sarah/Mark + fake commitments on a 2-sentence transcript because the prompt's Action Items section gave no empty-case instruction. Fix: prompt forbids inventing + writes "None mentioned." for empty sections, PLUS deterministic grounding.py (warn-only, flags ungrounded capitalized words). Verified with real twice-repeated inference. Lesson: a summary LLM fills template gaps with fabrication — constrain the empty case explicitly + keep a code-level grounding net.
- **BUG3 (closed): mic↔system track offset -28s scrambles transcript order.** First real solo test: Owner line rendered at [59:51], transcript out of order. Root cause was NOT the offset computation — 3 independent measurements (acoustic cross-correlation 28.36s, host-time delta 28.28s, same-utterance-position-in-each-track's-own-timeline 28.29s) all converged, confirming `computeMicStartOffset`'s sign was correct: mic's `AVAudioEngine.start()` is called first and starts near-instantly, while the CoreAudio tap's async setup (`AudioHardwareCreateProcessTap` → `AudioHardwareCreateAggregateDevice` → IOProc → `AudioDeviceStart`) took ~28s longer to produce its first sample, so mic genuinely started first. The bug was one level up: `_merge_dual_track_results` always shifted mic forward by `mic_offset` and left system unshifted, which is only correct when `mic_offset >= 0`. A negative offset (mic started first) pushed mic's early segments to negative timestamps, which `_format_time`'s divmod silently mangled into `[59:51]`. `MergeAudioFiles.swift`'s AUDIO merge already branched on `offsetFrames >= 0` correctly — only the Python TRANSCRIPT merge lacked the equivalent branch, so `recording.wav` itself was never corrupted. Fix: `_merge_dual_track_results` now anchors the timeline to whichever track started first, shifting the OTHER one forward — mirroring the Swift audio merge. Verified against the real repro data (`~/ownscribe/2026-07-24_1756_emerging-internet-force-impact/`) via `resume`: Owner now renders at [00:18], full chronological order. Lesson: when two async engines can start in either order, every downstream consumer of "the offset between them" needs the bidirectional branch, not just the one that happened to get exercised first.
- **BUG4: the menu-bar app could never record the owner's voice.** First real test of the installed .app (2026-07-27, solo in a Google Meet inside Dia): 33.5s captured, RMS exactly 0.0 on both channels, no transcript, no dual track. Two independent defects, and the reported symptom was neither. (a) `RecordingController.enableMic` defaulted to `false` and NOTHING in the app ever assigned it — no UI control, no settings path — so the mic track was structurally unreachable from the app while the CLI (`--mic`) was fine. (b) The silence itself was NOT a bug: alone in a Meet nobody else speaks, so the system output really was silent, and the owner's voice can only ever live in the mic track that (a) disabled. Discriminating the two required probing the SHIPPED bundle binary directly (`ownscribe-audio capture` while forcing real output) → peak 0.7588, proving tap + aggregate device + TCC grant all worked; then diffing the two call sites (`main.swift:608-618` vs `RecordingController.swift:77-89`) to show the capture sequence is byte-for-byte the same apart from `enableMic`. Lesson: a default-off flag with no writer is invisible to every test that constructs the object and drives it manually — assert on the DEFAULT the shipped path actually uses.
- **BUG5: the merge replayed the call at half speed.** `kSystemAudioSampleRate = 24000` (AudioLevels.swift) was used as the merge's `outputSampleRate` while capture writes at the hardware rate (48000 on this Mac). Because the mic path is resampled through `AVAudioConverter` but the system path is read raw, a 2s capture merged to a 4s file — voices deep and slowed, and every logged duration wrong by the same 2x (the shipped binary reported "22.0 seconds" for an 11.0s file). Same constant also fed `computeMicStartOffset`, i.e. a latent re-run of the BUG3 class. Fix: `outputSampleRate` follows `systemFile.processingFormat.sampleRate` (mic's as fallback for mic-only), and the tap reports duration from its own captured rate. The pre-existing offset tests hardcoded 24000 too, so they agreed with the bug and could never fail on it — the new tests write real 48k/44.1k WAVs and assert the merged file's duration and rate. Lesson: a test that reuses the constant under test is not a test; pin the OBSERVABLE (duration in seconds) instead.
- **The first real solo test (2026-07-24) is what proved the core works** AND surfaced BUG3 — system.wav captured real YouTube audio (-21dB), mic captured the user, diarization split Owner vs SPEAKER_00, summary grounded. Synthetic tests got the pipeline to "runs"; only real audio proved "works" + found the sync bug.

## Bugs caught during the build (by verification, not inspection)

- **13GB / 38.9h output from a 3s capture (pre-existing in ownscribe).** A CoreAudio tap temp file with real bytes but no `data` chunk (RIFF→JUNK→fmt→FLLR) fed a corrupt frame count into mergeAudioFiles. Fix: real frame-count check (`openAudioFileWithFrames`) instead of the byte-size heuristic. Git-stash-verified as pre-existing before fixing. Would have blown up on the first real call.
- **torchcodec fails to load (FFmpeg version mismatch).** Venv's torchcodec links FFmpeg 4-7 (libavutil.56-59); the machine has FFmpeg 8 (libavutil.60). Upgrading torchcodec needs torch≥2.9, conflicts with the torchaudio<2.9 pin → dead end. Fix: bypass torchcodec entirely — pyannote's Audio.**call** takes a preloaded `{"waveform","sample_rate"}` dict (checked FIRST, before the AudioDecoder path), which is exactly what _diarize() and whisperx.load_audio() already feed it. Pinned with a test asserting torchcodec never enters sys.modules.
- **Silent binary regression.** coreaudio.py downloaded ownscribe's UPSTREAM prebuilt binary when the local Swift build hadn't run (bin/ is gitignored) → separate-track retention silently regressed to merged-only, no error. Fix: `binary_supports_separate_tracks()` probe → fail loud instead of silently degrading.
- **mlx-audio ↔ whisperx dependency conflict (irreducible).** mlx-audio≥0.4.1 needs huggingface-hub≥1.0; whisperx caps <1.0. No config-only fix works (uv.lock pins one version project-wide regardless of extras/markers). Fix: Canary runs in a subprocess `uv run --with mlx-audio` overlay — never added to pyproject.toml. Base venv stays bit-identical.
- **AVAudioEngine self-pins the OUTPUT running-bit.** Starting a mic tap flips the default-output "running" bit true even in silence (framework render-graph artifact, not our code — bisected with 3 controls). Doesn't corrupt watch-activity today (watch + capture never run concurrently) but documented as a live constraint for any future concurrent consumer of that property.
- **W0-9 — You can record a whole meeting before learning nothing can transcribe it (2026-07-28).** `isCliAvailable` was computed correctly but had zero consumers. The user could start a recording, capture an entire meeting, then learn at processing time that the ownscribe CLI is missing — and the UI never said the audio survives. Unit of loss: an irreplaceable meeting. Fix: pre-flight check before recording start, plus a banner warning with corrected recovery text. The trap that would be easy to repeat: pointing users to `rec.sh redo <dir>` when the CLI is missing, when `redo` itself runs `.venv/bin/ownscribe` — the very binary whose absence caused the failure. Corrected banner orders it: *"Audio will be recorded but not transcribed — the ownscribe CLI is missing. Restore it, then run ./rec.sh redo <dir> to transcribe this meeting from its retained audio."* Safe → fix → recover. Recording is ALLOWED (not disabled) because the meeting is irreplaceable. Seam trap caught by test 8: `refreshCliAvailability()` originally clobbered `pipelineRunner` unconditionally, destroying the injected `pipelineRunnerFactory` and disarming the test seam. Fixed by checking if factory exists first and re-running it if present.
- **W0-4 — The sidebar's action and anchor filters are dead in production (2026-07-28).** The counts existed in the model (`actionItemsCount`, `unanchoredClaimsCount`) but no writer populated them, so both filters were always empty. Scoped as cheap (0.44 ms/refresh, no cache needed), but the trap is in the type: zero of six meetings on disk have `anchors.json`, so the counts must be `Int?` rather than `Int` — rendering an absent count as `0` claims *"all claims have evidence"* for meetings that were never checked, which is the W0-1 anti-hallucination signal failure. Absence → nil → grayed-out text or distinct UI state. Rule that generalizes: when a count's source file may not exist (a late-added feature file, a deferred check), make it `Int?` so absence cannot masquerade as zero.

## Process lessons

- **Empirical > recalled specs.** The Canary brief had 4/5 technical details wrong (they came from an HF model card, not the source): mlx-audio version (0.4.1 not 0.2.x), `language=` handling, `no_repeat_ngram_size` (doesn't exist), the "15s window" (conflated with a different model's VAD). All caught by reading the real source + isolated repro before writing code. Same for the "MPS broken" premise — the 2022 bug was fixed in torch 2.3; verified with a live repro on torch 2.8.
- **Disk is ground truth, not a message saying "we built X".** Two lead directives (CoreAudio tap; mic-activation trigger) were reported as decided/built but weren't in the code — caught by grepping the actual repo, not trusting the message.
- **Don't delete an artifact before independent verification.** The 60-min thermal results dir was cleaned up before the lead could verify it → had to reconstruct from the harness-persisted tool-output. Leave artifacts until signed off.
- **GDPR Art.9 (voiceprints = biometric data) is cleared for this use** (user confirmed authorized). Still: keep the repo PRIVATE, keep a "call is transcribed" notice, define a retention/purge policy.
- **A plumbed value is not a working feature.** The 2026-07-27 review's worst find: `silence_timeout` travelled config → AppState → controller → tap correctly, and the tap fired `onSilenceTimeout` into a nil optional because the CLI was its only assigner. Every link looked right in isolation. Trace a feature to its CONSUMER, not to the last assignment.
- **Four independent readings, four disjoint finding sets.** An automated review, a lead audit, an adversarial re-executing reviewer and a late planner ran on the same diff; each found defects the other three missed, and the highest-severity one surfaced two hours after the batch was declared done. Redundant review angles are not waste — but they only pay off if the later ones are not told "it's already been reviewed".
- **A test that fails then passes can still guard nothing.** Three of this batch's own tests were decorative, all caught by mutation, never by reading: a bare `XCTAssert(true)`; assertions on a spy property instead of the child process (`process.environment` could be deleted with all 3 tests green); and `XCTAssertFalse(phase == .recording(startedAt: Date()))`, which compares against a *fresh* `Date` so it is false in every state, including the one it exists to reject. Mutation-check the guard: break what it defends, watch it go red.
- **A test-only method in production is the same smell twice.** `lastProcessEnvironment` and `fireSilenceTimeoutForTest()` both existed solely for a test, and both let the test bypass the code under test. The second also retained a plaintext token in memory. If a test needs a seam, inject a fake at the boundary (`makeSystemCapture`, `mergeAudioFilesImpl`) rather than adding a hook that skips the real path.
- **Fixes interact.** Adding `cpu_threads` validation made `rec.sh`'s token check report "No HuggingFace token found" on a config with a valid token and an unrelated typo, because the shell read any non-zero exit as "missing". Neither task could reveal it alone; a cross-fix probe did.
- **The verification itself can fail silently.** `timeout` does not exist on macOS, so mutation runs returned EMPTY output that reads exactly like "the test passed". `swift/.build` copied to /tmp fails to *compile* (path-pinned module cache), which reads like "the test failed, so it discriminates". Python's `ownscribe.pth` hardcodes the main checkout, so an isolated copy silently imports the live tree. Prove which tree loaded and that the command actually ran before believing any result.

## Thermal (verified)

large-v3 CPU on this Mac: 165 back-to-back transcriptions over a real 3605s hour, mean RTF 0.717 (well under 1.0), peak RSS 9.3GB, zero thermal warnings across 122 samples. Sustained-hour envelope holds.
- **A green suite proves nothing about the call site.** The 2026-07-27 Glass batch shipped two features that were dead in production while their tests passed: claim anchoring returned `{}` on every real run because the call site passed `result.full_text` (one line, no timestamps) while six tests hand-built the timestamped markdown production never emits; and an envelope reference test re-implemented the file read inline, so replacing the production reader with `return zeros` left it green. Four instances of one shape in a single batch, including two of the lead's own replacement tests. Rule: the test must INVOKE production with production's own argument, and be parametrised over the config that changes that argument — `output.format` hid a JSON-only failure through three rounds of review.
- **A fix can be correct by luck.** Anchoring's false-positive fix was unreachable dead code (`rstrip()` then testing for a prefix ending in a space) and only *looked* fixed because English summary boilerplate does not appear in a French transcript. Against an English transcript the three original false positives returned. Then the presence-check replacement nearly reintroduced them from the other direction, because whisper sentence-cases every utterance — measured 72 of 72 — so the final rule counts only *mid-sentence* capitals as proper-noun evidence. When a guard passes, check whether it passes on the input distribution or only on the fixture.
- **Auditing a live working tree produces phantom failures.** Five times in one evening a reviewer caught the tree mid-write (1, 2, 3 failed, and once a whole-module `NameError` collection error that self-resolved in 35 s). None were defects. Disk mtime is what separates a race from a regression; a stable-for-N-seconds precondition before any suite run makes it mechanical.
- **The mute path is mutation-verified, so a future change has a baseline to fail against.** An independent Swift audit (2026-07-27) ran eight mutations over the shipped code and every guard held: collapsing `MuteIndicator` to always-verified → 1 red; cutting `restoreUnmutedOnQuit`'s retry loop to a single attempt → 1 red; and **dropping the verify-after-set read-back in `setSystemMuteVerified` → 6 reds**, making the guard the SKILL calls mandatory the most heavily tested thing in the file. Exit paths were enumerated by grep rather than assumed: `⌘Q`, force-quit and logout all route through `willTerminateNotification`, plus the SIGTERM/SIGINT sources and the menu Quit button — no uncovered path. If you touch this code, these are the mutations to re-run.
- **A fix that lands in source can still be absent from production, and BUG5 shipped that way for three days.** `coreaudio.py:_find_binary()` prefers `bin/ownscribe-audio` over anything in `.build`; `bin/` is gitignored (`.gitignore:27`) and only `swift/build.sh` copies into it. So after the BUG5 fix (`db1dae7`, Jul 27 14:09) the binary the pipeline actually ran was still dated Jul 24 17:07. Measured on one real dual-track capture: `bin/` produced `recording.wav` **12.81s @24000Hz** from 48 kHz sources, `.build/` produced **5.52s @48000Hz**. The signature is visible in the user's own retained meetings — the two from July 24 are 24000Hz. **My new e2e tests could not see it, three ways:** they hardcoded the `.build` path; `--help` is byte-identical between the two binaries so the smoke test passed against the broken one; and they never passed `--mic`, so `mergeAudioFiles` — where BUG5 lives — was never reached at all. Worse, the duration bound I wrote could not have caught it even on the right binary: 12.81s from a ~5s capture sits inside `1.0 <= d <= 30.0`, while that assertion's own message claimed to guard the 2x class. Fixes: resolve the binary through production's own `_BINARY_CANDIDATES`, drive `--mic`, and assert the merged rate **equals** its sources' rather than bounding a duration; plus a `check.sh` gate comparing `bin/` against every Swift source. Rules: **ask which artifact production loads, not which one you just built**, and pin the observable that the bug changes (a rate) rather than one it merely perturbs (a duration). Found by an agent auditing my own tests adversarially — worth more than another feature.
- **Restoring a backup with `cp` refreshes the mtime and can hide the condition you are testing.** My first mutation of the staleness gate copied a stale binary back into `bin/` and the gate reported "ok" — I nearly concluded my own guard was decorative. The `cp` had stamped it with the current time, so it was no longer stale. Re-run with `touch -t 202607240000` and the gate failed correctly, naming the newer source file. When a mutation unexpectedly survives, verify the mutation actually took effect on the property being read — mtime, file size, a symbol — before believing the guard is at fault.
- **Widening a setter for a test is the banned test-only method under another name.** W0-7's first version changed `AppState.phase` from `public private(set)` to `public internal(set)` so four tests could write it — the same `forcePhaseForTesting` pattern deleted from that exact file hours earlier, except permanent and module-wide. The deeper problem was what the writes bought: `phase = .recording(startedAt:)` does not start a recording, because `recordingController.state` stays `.idle` and **nothing reconciles the two**. So the test proved "dismissFailure ignores an enum value", while its own assertion message claimed "must NOT abort a live recording". Reworked to reach `.failed` by driving a stop with no CLI available, and `.recording` through the capture seams; two tests were **dropped** rather than rewritten because `.processing` and `.done` are not reachable without the MainActor choreography that deadlocked twice that morning. The mutation count fell from a flattering 3 to an honest **1** — which is the truer measurement, not a weaker one. Ask of any forced state: can production produce this, and does anything downstream have to agree with it?
- **"Needs the user" is often "needs the right hardware attached".** The two mute checks were carried as user-only for days. The moment the AirPods disconnected and the built-in mic became the default, both became automatable — because the one case the suite genuinely cannot assert against is the documented macOS *Bluetooth* mute bug, where a red would not distinguish our logic from the platform. Now `RealHardwareMuteTests` mutes the real device, asserts, and mutation-verifies. The pattern that makes a dangerous real test safe: `setUp` records the state it found and skips if it cannot READ it (no restore is possible otherwise), `tearDown` restores it **and asserts the restore**, and the suite skips itself on the fragile hardware class. Verified the teardown holds on the failing path too — after a mutation run that went red, the mic was still restored. Before deferring a check to the user, ask which specific hardware condition blocks it and whether it currently holds.
- **A real end-to-end test earns its cost by correcting your assumptions, not by going green.** Writing `tests/test_real_capture_e2e.py` against the shipped `ownscribe-audio` immediately falsified three beliefs the mocked suite had let stand: the binary has no `--duration` flag (it records until SIGINT), it prints usage on **stderr** not stdout, and it writes **IEEE float32**, which Python's stdlib `wave` rejects with `unknown format: 3` — so the test must read via `soundfile`, the same float32 `envelope.py` deliberately depends on. All three were invisible to 617 passing tests that mock `subprocess`. One further trap: the tap records what the machine OUTPUTS, so on a muted or silent system it correctly produces a valid 48 kHz stereo float header with **zero frames** — my first version captured that silence and blamed the binary, when the fix was to PLAY audio during capture (`afplay`) so there is something to record. Mutation: replacing the playback with a sleep turns 2 of 5 red. And a mutation run inside a `git worktree` gave 5 instant reds that were a **false positive** — `.build` is gitignored, so the binary was absent; the giveaway was 0.44s versus the 16s a real capture takes.
- **The test suite hijacked the real microphone, and the object's CONSTRUCTOR was the culprit — not its `start()`.** The user reported the Mac's audio had gone bad; it tracked to `swift test`. Measured with `/usr/bin/log show | grep -cE 'PauseIO|ResumeIO'`: **0 cycles in the 20 s before a run, 7920 after**, and the AirPods Max input pinned at **24 kHz** (the HFP "phone call" profile) instead of 48 kHz, which dulls playback in every app until macOS renegotiates. Two ways in: the silence-timeout tests never set `isMicCaptureEnabled = false`, and a missing config file means **mic ON** by design (`mic ?? true`), so a temp `homeDir` silently opted them in; the merge tests set `enableMic = true` explicitly and injected no capture at all, opening a real mic *and* a real CoreAudio tap. **The instructive part: injecting a `startMicCapture` seam did not fix it** — bisection showed the same suites still cycling. `MicCapture` holds `private let engine = AVAudioEngine()` as a **stored property**, so the input device is claimed when the object is *constructed*, before any `start()` runs. For a type that grabs hardware in `init`, the seam must control **construction** (`makeMicCapture`), not just starting. Rules: a test that reaches `start()` must inject BOTH captures; a default-ON flag plus a temp home is a silent opt-in, so assert the default your tests inherit; and when a test genuinely needs hardware (`stop()` only merges with a live `micCapture`), gate it behind an env var and keep a hardware-free test for the same guarantee rather than losing the coverage. Diagnostic tool worth reusing: bisect suite-by-suite against the log counter — it named the source in one pass after two wrong hypotheses.
- **A first diagnosis that fits the evidence can still be the wrong cause.** I blamed a third-party notch app polling Bluetooth 7905 times in 20 minutes — real, measured, and correlated with the cycling. The user rejected it on better grounds: that app had run for days without trouble, and the problem began with my changes. **Correlation with a loud process beat causation from my own code**, and the user's temporal evidence was stronger than my volume evidence. When someone says "it started when you changed X", weigh that above a suspicious-looking bystander, and bisect your own work first.
- **When several consumers read one string, the cheap one passes and the expensive one is the real gate.** W0-6 (unique meeting directory) took six attempts, and every rejected one was green on its own tests. `MeetingSummary` derives two display values from the directory name: `displayDate` splits on `_` and needs `parts[1]` to be exactly `HHmm`, `displayTitle` takes `parts[2]` as the slug. **Every candidate name parsed the date; only one kept the title** — so a round-trip test built on `displayDate` (the obvious consumer, and the one the first bug broke) passed on every subsequent wrong answer. The four measured failures: `-2` appended to the minute field blanks the date; `_2` between timestamp and slug makes the title read `2_project review`; `-tmp2` blanks the date again; and a greedy `^(.+)_\d+$` strip pattern turns `2026-07-28_1234` into `2026-07-28`, because `1234` is itself `\d+` — that one would have blanked the date on EVERY meeting, collision or not, which is worse than the bug being fixed. Rules: **enumerate all consumers of a format before changing it** (`grep -rn lastPathComponent`), assert on the *output of each* rather than on the string's shape, and treat "it parses" as necessary and never sufficient. A regex or format string is free to probe — five lines of Python caught the greedy bug that four rounds of reasoning had waved through.
- **A test that types a value production just computed cannot see a format change.** The last W0-6 test hand-wrote `"2024-01-28_1310_project-technical-review-2"` two lines after building a real `MeetingOutputPaths` at that same instant, justified as "Swift cannot produce Python's output". Half true: the slug is Python's, but the timestamp was already in hand. Deriving it widened the mutation kill from 4 of 9 to **5 of 9** on the same file — the literal was silently costing a guard. If a test contains a date literal inside a directory name, it is asserting about a name the app may never emit.
- **A crash report names the frame that trapped, not the code that is wrong — and an agent's throwaway test can look exactly like a production defect.** A handoff from another session (`~/Desktop/handoff-xctest-coreaudio.md`, 2026-07-28) traced five `xctest` SIGTRAPs to `EnrolledSpeakerStore.names(in:)` and recommended replacing an `assertionFailure` on malformed input with a graceful return. Its measurements were sound — 4 crashes in 55 s, and CoreAudio/Bluetooth cycling at ~20x baseline (`BTAudioHALPlugin register` 1054/60s vs 52/60s at rest) tracked the presence of `xctest`, which is a real causal link worth knowing. But the recommended fix would have edited code that has no defect: `names(in:)` contains **zero** `assertionFailure` — it is two `try?`s returning `[]` — and `git log -p --all` on that file shows the string never appeared in its history. `_assertionFailure` is Swift's generic trap symbol for a runtime precondition, and the frame above it in the same stack is `Array._checkSubscript` → an out-of-bounds index. The `usedImages` path settles the provenance: every one of the five ran from `/private/tmp/*/ownscribe-audioPackageTests`, i.e. isolated **copies** made by review agents, not the repo — and the crashing frames belong to those agents' scratch test files (`DesignCheckClaim3Tests`, plus index-based assertions in `TranscriptDocumentTests`). The repo's own suite was green throughout (186 tests, 0 failures). Two rules from this: attribute a trap to the frame that *indexes*, not the one that *traps*, and check the crashing bundle's path before touching production — an audit copy under `/tmp` is not this codebase. Also: agents' throwaway tests that subscript an array (`doc.utterances[2]`) trap instead of failing, killing the whole `xctest` process and taking the run's results with it; prefer `XCTAssertEqual(doc.utterances.count, n)` first, or `.dropFirst().first`.
- **A test that needs a precise interleaving on a serial actor is the wrong instrument — and it deadlocks instead of failing.** Verifying that a finishing pipeline cannot clobber a live recording seemed to need the real interleaving: suspend `runPipeline` inside a fake runner's continuation, start a second recording, then resume. Two attempts HUNG — 23 minutes and 6 minutes — each holding the SwiftPM `.build` lock and blocking two other agents; the lead's own instruction to "model production's fire-and-forget `Task {}`" was the wrong advice and was retracted. Root cause read off a real backtrace (`lldb -p <pid> --batch -o "thread backtrace all"` → frames #7-#11 `XCTWaiter._synchronouslyWaitForTimeInterval` → `waitForExpectations`): `AppState`, the fake runner AND the `XCTestCase` body are all `@MainActor` while XCTest pumps a CFRunLoop on that same thread, so the three-way ordering the test required cannot be forced by `Task.yield()` — when it does not happen, the continuation is never resumed and the test hangs forever rather than reporting. Fix: extract the DECISION from the choreography — a pure `terminalPhase(after:completedWith:)` returning nil unless the phase is still `.processing`. Same claim, 7 tests, 0.001s, and it mutation-checks cleanly (success guard → 4 red, failure guard → 1 red, guarded independently). **A deadlocking test is worse than a failing one and must be deleted, not skipped:** it cannot report, and it blocks every other build on the machine. Corollary for diagnosis: this package's whole suite runs in ~38s, so a `swift test` past ~90s is hanging, not building — and `lldb` on the stuck pid names the cause in one command.
- **The fix for a lying indicator can create a worse lie.** Seeding `isMuted` from `readInputMute()` at launch closes a real defect (a mic muted by a crash or another app read as live, so you join a call believing you are heard). But `restoreUnmutedOnQuit` fires on every exit path, so seeding alone would make the app **silently unmute a mute the user made themselves in System Settings** when it quits — a false sense of mute in a live call, i.e. trading a stale display for the exact failure class the whole mute path exists to prevent. The state therefore has to distinguish a mute this app PERFORMED from one it merely OBSERVED; ownership is taken only when a set is confirmed by read-back, and an observed mute is displayed truthfully and never undone. Reverting `guard isMuted, appOwnsMute` to `guard isMuted` turns 2 tests red; reverting the seeding turns 8 red. Lesson: before making a display reflect reality, check every consumer that ACTS on that display.
- **Two properties passed 160 tests while being replaceable by a constant.** `AppState.isRecording` → `return false` left the whole suite green, yet its only consumer is the window's record button, which would then read "Enregistrer" during a live recording — UI asserting a state it never verified, the same class as the mute-icon bug fixed hours earlier.
